# 골격 후속 정리(Post-Skeleton Cleanup) 설계

## 1. 목적과 범위

이커머스 골격 사이클의 최종 코드 리뷰에서 식별된 Minor 이슈 4건을 해소한다.
사용자 동작 변경은 없고(④의 DB 제약 추가 제외), 코드 품질·설정 유연성·데이터 무결성을 개선한다.

### 포함 (In scope)

1. 프론트 메타데이터 정리 (`layout.tsx`)
2. 서비스 `create()` 이중 세팅 정리 (생성자 오버로드)
3. DB 접속 정보 환경변수 외부화 (`application.yml`)
4. 시드 멱등성을 DB 유니크 제약으로 보강 (`Supplier.name`)

### 제외 (Out of scope, 이후 사이클)

- 인증(Spring Security) 도입
- 어드민 CRUD 폼, 페이지네이션, 스타일링 고도화
- Flyway/Liquibase 등 마이그레이션 도구 도입

## 2. 변경 상세

### ① 프론트 메타데이터 정리 — `frontend/src/app/layout.tsx`

- `title: "Create Next App"` → `"이커머스 스토어"`
- `description: "Generated by create next app"` → `"공급사별 상품을 판매하는 이커머스 스토어"`
- `<html lang="en">` → `lang="ko"`
- 그 외(Geist 폰트, className)는 변경하지 않는다.

### ② create() 이중 세팅 정리 — `Supplier.java`, `Product.java`, 두 Service

현재 `create()`는 생성자가 status를 기본값으로 하드코딩한 직후 `update()`로 요청 status를
덮어쓴다(이중 세팅). status를 받는 생성자를 추가해 한 번에 올바른 상태로 생성한다.

```java
// Supplier.java — 생성자 오버로드 추가
public Supplier(String name, String contactEmail) {
    this(name, contactEmail, SupplierStatus.ACTIVE);  // 기존 호출부 호환
}

public Supplier(String name, String contactEmail, SupplierStatus status) {
    this.name = name;
    this.contactEmail = contactEmail;
    this.status = status;
}
```

- `Product`도 동일 패턴 (`ProductStatus` 파라미터를 받는 생성자 추가).
- `SupplierService.create()`: `new Supplier(name, email, request.status())` 사용, `update()` 호출 제거.
- `ProductService.create()`: 동일하게 정리.
- `DataSeeder`·기존 테스트는 기존 생성자 시그니처를 그대로 사용하므로 **②로 인한** 수정은 없다
  (단, `DataSeeder`는 ④에서 멱등성 체크 방식이 별도로 변경된다).

### ③ DB 설정 외부화 — `application.yml`

```yaml
datasource:
  url: ${DB_URL:jdbc:mysql://localhost:3306/ecommerce?serverTimezone=UTC&characterEncoding=UTF-8}
  username: ${DB_USERNAME:ecommerce}
  password: ${DB_PASSWORD:ecommerce}
```

- 기본값 = 현재 로컬 값이므로 로컬 개발 경험은 변하지 않는다.
- 운영 배포 시 환경변수로 오버라이드한다.

### ④ 시드 멱등성 보강 — `Supplier.java`, `SupplierRepository.java`, `DataSeeder.java`

- `Supplier.name`: `@Column(nullable = false, unique = true)` — 공급사명 중복을 DB 레벨에서 차단.
- `SupplierRepository`에 `boolean existsByName(String name)` 추가.
- `DataSeeder`: `count() > 0` 체크 → 첫 번째 시드 공급사명(`"신선식품 주식회사"`)의
  `existsByName()` 체크로 변경. 동시 기동 race가 발생해도 유니크 제약이 최종 방어선이 된다.
- 기존 주석의 "운영 전에는 DB 유니크 제약으로 보완 필요" 문구는 해소되므로 제거.

## 3. 테스트 전략

| 항목 | 검증 방법 |
|------|----------|
| ② | 기존 테스트 회귀 + status를 기본값이 아닌 값(`INACTIVE`/`HIDDEN`)으로 생성하는 테스트 추가 |
| ④ | 중복 공급사명 저장 시 제약 위반(DataIntegrityViolationException) 발생 리포지토리 테스트 추가 |
| ① | `npm run build` 통과 (수동: 브라우저 탭 제목 확인) |
| ③ | 기존 컨텍스트 로딩 테스트 (플레이스홀더 문법 오류 시 기동 실패로 감지) |

## 4. 마이그레이션/주의사항

- `ddl-auto: update`는 기존 `suppliers` 테이블에 유니크 제약을 추가하지 못할 수 있다.
  → 로컬 검증 절차에 `docker compose down -v`(볼륨 삭제 후 재생성)를 포함하고, README에 안내를 추가한다.
- H2 테스트 DB는 `create-drop`이므로 영향 없다.

## 5. 검증 기준 (Definition of Done)

1. `./gradlew test` 전체 통과 (신규 테스트 포함)
2. `cd frontend && npm run build` 통과
3. 브라우저 탭 제목이 "이커머스 스토어"로 표시된다
4. `DB_PASSWORD` 등 환경변수 설정 시 해당 값으로 DB 접속을 시도한다
5. 동일 공급사명 중복 저장 시 DB 제약 위반이 발생한다
